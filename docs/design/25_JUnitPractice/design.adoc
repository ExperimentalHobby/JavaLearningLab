== 概要

=== 目的
注文確認メールを送信する `OrderNotificationService` を題材に、Mockitoによるモックテストを実践するミニアプリを提供する。TDDとMockitoを使ったモックテストの実践を目的とする。

=== 主な機能
* `order <メールアドレス> <金額>` で注文確認メールをコンソールへ表示するデモを体験する
* `exit` によるアプリ終了

=== 開発環境
[cols="1,3", options="header"]
|===
| 項目 | 内容

| 言語
| Java 25

| ビルドツール
| Maven(フォルダ単位で独立した `pom.xml`)

| テスト
| JUnit 5 + Mockito(`mockito-junit-jupiter`、`@ExtendWith(MockitoExtension.class)` + `@Mock`)

| メール送信
| `EmailSender` インターフェース(デモ用実装は `ConsoleEmailSender`)
|===

=== 実行方法
[source,powershell]
----
cd 25_JUnitPractice
.\mvnw.cmd compile
.\mvnw.cmd test
.\mvnw.cmd exec:java "-Dexec.mainClass=com.javalab.junitpractice.Main"
----

== 補足事項

=== モックが適切な場面としての位置づけ
01〜24では一貫して「実リソースでのテスト(実HTTPサーバー・実DB・実Socket等)」を用いモックを避けてきたが、本課題は学習ポイントとして明示的にMockitoを扱うため、あえてその方針と対比させた。`EmailSender`(実運用ではSMTP/SES等の外部サービスに依存)は実際に送信すると副作用が大きく実リソースでのテストに向かないため、モックが適切な場面の実例になっている。

=== Mockitoの基本APIの実践
`org.mockito:mockito-junit-jupiter` を使い、`@ExtendWith(MockitoExtension.class)` + `@Mock` アノテーションという標準的な書き方で `EmailSender` をモック化した。`verify()` による呼び出し検証(引数一致・回数)、`doThrow().when()` による例外スタブ、`verify(never())` による「呼ばれていないこと」の検証まで、Mockitoの基本APIを一通り実践した。

=== Object由来メソッド名との衝突の教訓
当初 `notifyAll(List<Order>)` というメソッド名で実装しようとしたところ、`java.lang.Object` が持つ `notifyAll()`(スレッド同期用の特殊メソッド)と名前が衝突し、コンパイラが引数なしの `Object.notifyAll()` へ解決してしまうという紛らわしいコンパイルエラーに遭遇した。メソッド名を `notifyOrders` に変更することで解消した。`Object` のメソッド名(`wait`/`notify`/`notifyAll`/`equals`/`hashCode`/`toString`等)との衝突は意図しない挙動を招きやすいため、独自メソッド名として避けるべき教訓として記録する。

=== Mockitoの既知の警告について
Mockitoの内部実装(バイトコード生成)がJDK 25の動的エージェント読み込みに関する警告を出すが、これはMockito自体がJDKの将来的な制限に向けて対応中の既知の警告であり、テスト結果やビルドには影響しない。

=== テスト方針(TDD)
Red → Green → Refactor サイクルで実装した。

* *単体テスト*(`OrderNotificationServiceTest`): Mockitoで `EmailSender` をモック化し、送信内容の検証・0円以下のスキップ・送信失敗時の例外・`notifyOrders` の複数件処理を検証
* *結合テスト*(`MainTest`): `order`コマンドの結果表示(`ConsoleEmailSender` の実出力を検証、モックではなく実際の標準出力ストリームを使用)、および不正なコマンド入力時にエラー表示してループを継続する動作を検証
