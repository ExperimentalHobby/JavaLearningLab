== 概要

=== 目的
再帰的バックトラック法で「完全迷路」(任意の2マス間の経路が一意に定まる迷路)を生成し、BFS/DFS/A*の3アルゴリズムでスタート(左上・緑)からゴール(右下・赤)までの経路を探索、JavaFXの `Canvas` に経路をアニメーション表示するツールを提供する。BFS/DFS/A*、Canvas描画、アニメーションの実践を目的とする。

=== 主な機能
* 「迷路生成」ボタンで新しい迷路を生成する
* アルゴリズム(BFS/DFS/A*)を選択する
* 「探索アニメーション開始」ボタンで経路を1マスずつ塗りつぶすアニメーションを表示する

`MazeVisualizerApp`(`Application` を継承したJavaFXメインウィンドウ)はアルゴリズム選択・アニメーション実行中状態という状態遷移を `MazeVisualizerState` に委譲し、自身はCanvas描画とタイマー操作のみを担当する。`MazeVisualizerState` は `MazeGenerator` で迷路を生成し、選択されたアルゴリズムに対応する `MazeSolver`(`BfsMazeSolver`/`DfsMazeSolver`/`AStarMazeSolver`)で経路を探索する。`Maze` は `Cell` 同士の接続をグラフとして保持する。

== 補足事項

=== テスト方針の分離
Issue #11/#18と同じ方針で、Canvas描画・アニメーション自体は自動テストが困難なため、`MazeGenerator` と各 `MazeSolver` はJavaFXに依存しない純粋なロジックとしてTDDし、GUI(`MazeVisualizerApp`)は実装後に実機起動・スクリーンショットで手動確認した。

UC-3(探索アニメーションを開始する)は本アプリの中核機能であり、11/18の対象UIより視覚的な振る舞いへの依存が大きい。それでもなお、`GraphicsContext` の呼び出し検証やスクリーンショット視覚回帰テストは導入しないという方針をIssue #85で最終決定した。`MazeVisualizerState`(下記参照)が「どの経路を・どの順序で返すか」というアニメーションの内容を既にTDDで保証しており、`MazeVisualizerApp` 側の `drawMaze`/`Timeline` はその結果を画面に描くだけの薄い層である。したがって、テストダブル・視覚回帰テストを導入しなくても退行時に検出できないのは「正しい経路が正しく画面に反映されているか」という描画の忠実性のみに限定される。この範囲は実機での手動確認で十分にカバーできると判断し、追加のテスト基盤への投資は見送った。

=== アルゴリズム選択・アニメーション状態の切り出し
当初「アルゴリズムに応じたソルバーの選択」「アニメーション実行中に迷路を再生成しても安全に停止・リセットされること」(UC-2〜4)が `MazeVisualizerApp` に直接実装されており、`Timeline`/`Canvas` に依存するためテストで検証できていなかった。特にUC-4(アニメーション中の再生成)は実行中タイマーの停止と状態リセットという非自明な挙動で、退行しても検出できない状態だった。

この状態遷移を `MazeVisualizerState` として切り出すことで、`Timeline`/`Canvas`/`ComboBox` に依存せずUC-2〜4をTDDで検証できるようにした。11_HouseholdBudgetGuiの `BudgetTableModel`、18_TextEditorSwingの `EditorDocument` 分離と同じ考え方を踏襲している。

=== 接続グラフとしての迷路表現
迷路は `Map<Cell, Set<Cell>>` で「通路として繋がっているマス」を表現している(壁の2次元配列ではなく接続グラフとして持つことで、生成・探索の両方をシンプルなグラフアルゴリズムとして実装できる)。

=== 再帰的バックトラック法と全域木
`MazeGenerator` は `seed` 付き `Random` で再帰的バックトラック法(スタック使用の反復版、深い再帰によるスタックオーバーフロー回避)を実装し、同じseedなら常に同じ迷路が生成されることをテストで保証した。再帰的バックトラック法は必ず全域木(スパニングツリー)を生成するため、任意の2マス間の経路が一意に定まり、BFS/DFS/A*はどれも同じ経路を返す(探索順序・訪問順は異なる)。

=== ソルバーの単体テスト戦略
ソルバーのテストは、生成された迷路ではなく手動で組み立てた小さな迷路(3マスの直線)を使い、アルゴリズムの実装そのものを検証した。到達不可能なケース(通路を繋がない2マス)では空リストを返すことも確認した。

=== JavaFXの既知の制約とその回避
`main` メソッドを持つクラスが直接 `javafx.application.Application` を継承していると、クラスパス実行時に「JavaFXランタイム・コンポーネントが不足しています」というエラーになった。`Application` サブクラス(`MazeVisualizerApp`)とエントリーポイント(`Main`、`Application.launch(MazeVisualizerApp.class, args)` を呼ぶだけ)を分離することで解決した。

=== 環境依存の対応
依存関係のクラシファイアは開発機がWindows専用のため `win` に固定した(`javafx-controls`/`javafx-graphics` 24.0.1)。Java 25でもビルド・実行とも問題なく動作することを確認済み。実機での手動確認では、通常のハードウェアアクセラレーション(Direct3D)描画だとスクリーンショット取得環境で画面キャプチャに描画内容が反映されなかったため、確認時のみ `-Dprism.order=sw`(ソフトウェアレンダリング)を指定して迷路描画・探索アニメーションが正しく動作することを確認した。通常の対話的環境では既定のハードウェアアクセラレーションで問題なく動作する想定。

=== テスト方針(TDD)
Red → Green → Refactor サイクルで実装した。

* *単体テスト*: `MazeGenerator` の同一seedでの再現性、各 `MazeSolver` の経路探索(手動迷路)・到達不可能ケースを検証
* *単体テスト*(`MazeVisualizerStateTest`): アルゴリズム名から対応するソルバーが選択されること・未知の名前で例外を送出すること、`startAnimation`が経路を返しアニメーション実行中状態になること、`generateMaze`がアニメーション中でも実行中状態をリセットすること(UC-4の核心)を検証
* *手動確認*: `MazeVisualizerApp` のウィンドウ表示・Canvas描画・探索アニメーション表示を実機で確認(ソフトウェアレンダリングでスクリーンショット取得)
